## comms-protocol — Agent Communication Protocol Established
**Time:** 05:56 UTC | **Agent:** cto | **Task ref:** ceo-20260325-002

### Decision
`COMMS_PROTOCOL.md` defines three typed JSON message schemas — delegation, result, escalation — as the mandatory contract format for all inter-agent communication. Approved by CEO without revision.

### Context
No formal inter-agent communication contract existed. Agents communicated informally via `sessions_send` with unstructured messages. This makes workflows untraceable and contracts unenforceable.

### Options considered
- **Option A:** Lightweight convention (prefix + free text) — rejected, still untyped and unenforceable
- **Chosen:** Typed JSON schemas with mandatory fields — traceable, validatable, extensible to all tier chains

### Constraints
- No free-form delegation in automated flows
- One escalation per blocker — no stacking
- Workers write to Task DAG; they do not send messages to agents
- All contracts logged to trace log at send time
- Task ID format: `<sender>-<YYYYMMDD>-<seq>`

### Next action
Memory protocol (`MEMORY_PROTOCOL.md`) as immediate next deliverable.

## memory-protocol — Memory Protocol Established
**Time:** 06:00 UTC | **Agent:** cto | **Task ref:** ceo-20260325-003

### Decision
`MEMORY_PROTOCOL.md` defines write standards, file naming, store taxonomy, and retention rules for all five memory stores: `MEMORY.md`, `memory/YYYY-MM-DD.md`, ChromaDB, `heartbeat.md`, and `trace.jsonl`.

### Context
No memory write standards existed. Agents had no guidance on what to persist, where, or when — creating risk of institutional amnesia and duplicated work across sessions.

### Options considered
- **Option A:** Single flat `MEMORY.md` for all decisions — rejected, no retention management, becomes unwieldy
- **Option B:** Fully database-driven (ChromaDB only) — rejected, ChromaDB not yet deployed; markdown files are immediately usable
- **Chosen:** Tiered system — markdown index + daily files for active decisions, ChromaDB for long-term archive. Works now; scales to full stack on Q2 deployment.

### Constraints
- Write immediately — same session as the decision
- Workers do not write to shared memory (→ Task DAG only)
- One decision per entry — no batching
- Daily files archived to ChromaDB after 90 days, then deleted

### Next action
Security audit and identity configuration — parallel tracks, both can start now that architecture, comms, and memory are baselined.

## chromadb-write-access — CAO as Sole ChromaDB Write Gateway
**Time:** 05:54 UTC | **Agent:** cto | **Task ref:** ceo-20260325-001

### Decision
All ChromaDB writes route through the Digital Archivist (write-only worker) under CAO management. The COO gateway process does not write to ChromaDB directly.

### Context
During architecture design, a question arose: should the COO gateway (which spawns workers and receives task results) write directly to ChromaDB for speed, or route through the CAO-managed Digital Archivist?

### Options considered
- **Option A:** COO direct write — lower latency, simpler implementation. Breaks single-writer principle; two agents with write access create concurrent write risk and split auditability.
- **Chosen:** Digital Archivist (write-only, under CAO) — preserves single-writer principle. CAO is the authoritative owner of the knowledge base. One extra hop per task completion is acceptable.

### Constraints
Digital Archivist = write-only (no read). CAO = read + manage. Hallucination Hunter = read-only. No other agent has ChromaDB write access.

### Next action
Implement Digital Archivist spawn trigger in COO gateway — Q2 milestone.

## instance-status-format — Instance Status Display Standard
**Time:** ~09:00 UTC | **Agent:** cto | **Task ref:** ad-hoc

### Decision
`instance` command outputs a two-panel fixed-width block:
- Left panel: timestamp, per-agent context, CPU/RAM/DISK/UP/AGENTS/GATEWAY/TAILSCALE/SLD
- Right panel: CONTEXT per agent (today), COST per agent in USD + TOTAL in USD and SEK
- SLD shows ✓ when domain configured, ✗ when not
- SEK rate fetched live from Frankfurter API
- Cost fetched via sub-agent (sessions_list aggregation)
